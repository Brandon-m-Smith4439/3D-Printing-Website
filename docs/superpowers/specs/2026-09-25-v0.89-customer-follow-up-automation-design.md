# v0.89 Customer Follow-up Automation Design

**Status:** Proposed for implementation after owner review  
**Target release:** v0.89  
**Source baseline:** GitHub `main` after v0.88 EasyPost completion  
**Production stack:** Next.js 16.3.5 App Router, React 19, Node 22, SQLite on Railway persistent volume, Resend

## Purpose

v0.89 adds safe, auditable customer follow-up automation for requests that are waiting on a quote response, deposit, final-balance payment, or an owner-marked customer reply.

The goal is to reduce manual chasing without creating duplicate, excessive, or inappropriate email. The system must reuse the existing customer account, notification, quote, invoice, audit, Operations Center, and Resend infrastructure rather than introducing a second messaging stack.

This release is intentionally limited to transactional workflow reminders. It must not send marketing, promotional, newsletter, or cross-sell content.

## Existing system to preserve

The current application already provides:

- `lib/customer-notifications.ts` for in-app notifications plus optional Resend email.
- Customer email verification and `emailStatusUpdates` preference checks.
- Per-request `emailNotifications` preference.
- Quote timestamps and status transitions in `lib/quote-store.ts`.
- Deposit accounting and outstanding-balance helpers in `lib/quote-types.ts`.
- Final invoice timestamps, status, due date, and balance in `lib/final-invoice-store.ts`.
- Owner audit records in `lib/audit-log.ts`.
- Operations Center attention and health reporting.
- One production Railway service with one persistent SQLite volume.

v0.89 must extend these boundaries instead of bypassing them.

## Design decision

Use an **idempotent hourly follow-up sweep inside the existing Next.js Node service**.

The scheduler will start from root `instrumentation.ts`. Next.js documents `instrumentation.ts` as stable and calls its optional `register()` function once when a new server instance starts. The root register function will only initialize a Node-side scheduler and will return immediately; it will not make startup wait for a reminder sweep.

The scheduler will:

1. wait briefly after process startup,
2. run one sweep,
3. repeat approximately once per hour,
4. use persistent follow-up records so restarts do not lose history,
5. guard against duplicate delivery with deterministic business-event IDs and Resend idempotency keys,
6. avoid keeping the process alive solely for the timer by using unreferenced Node timers.

No second Railway service, external queue, or new paid infrastructure is required.

## Release safety gates

Automatic sending has two gates:

1. Deployment gate: `CUSTOMER_FOLLOWUPS_ENABLED=false` by default.
2. Owner setting: persisted master `enabled=false` by default.

A reminder is sent only when **both** gates are enabled.

The owner can always run Preview / Dry Run regardless of the gates. Preview computes current candidates and blocking reasons without sending email and without consuming reminder stages.

The first v0.89 production deployment must leave both gates off. Production data is previewed first. The environment gate may then be enabled, but the owner master switch remains available as a fast pause control.

## Reminder types and cadence

### Quote response reminders

Eligibility:

- request is active, not completed or declined,
- current quote exists,
- quote status is `sent`,
- quote has a valid `sentAt`,
- customer has not approved, declined, or countered that revision.

Stages:

- Reminder 1: 48 hours after `sentAt`.
- Reminder 2: 5 days after `sentAt`.

Maximum: 2 reminders per quote revision.

A new quote revision creates a new reminder anchor. Old-revision candidates are no longer eligible.

### Deposit reminders

Eligibility:

- current quote status is `approved`,
- customer approval timestamp exists,
- required 50% deposit is not fully reconciled,
- `quoteDepositOutstandingCents(quote) > 0`,
- no refund condition or quote state makes the payment workflow invalid.

Stages:

- Reminder 1: 24 hours after `approvedAt`.
- Reminder 2: 4 days after `approvedAt`.

Maximum: 2 reminders per approved quote revision.

The reminder stops immediately when the current quote becomes `deposit-paid`, is revised, voided, declined, or otherwise no longer eligible.

### Final-balance invoice reminders

Eligibility:

- latest final invoice is `open`,
- `amountRemainingCents > 0`,
- invoice has not been paid, voided, or marked uncollectible.

Stages:

- Reminder 1: 24 hours after `sentAt`.
- Reminder 2: first scheduler pass at or after `dueDate`.

Maximum: 2 reminders per Stripe invoice.

If `dueDate` is absent, the overdue stage is not created.

### Owner-marked waiting-on-customer reminder

This is not a new request workflow status.

The owner may mark a request as **Waiting on customer**. That control stores:

- request ID,
- active flag,
- `waitingSince`,
- optional short owner note,
- updated timestamp.

One reminder becomes due 72 hours after `waitingSince`.

Maximum: 1 reminder per waiting cycle.

Clearing and later re-marking the request creates a new cycle because `waitingSince` changes.

This generic reminder is lower priority than quote, deposit, or invoice reminders. If a state-specific reminder is due, the generic waiting reminder must not create a second email in the same cooldown window.

## Customer eligibility and consent

Automated email is allowed only when all of the following are true:

- request has a linked `customerAccountId`,
- the customer account exists,
- the account has `emailVerifiedAt`,
- the effective email preference is enabled:
  - request-level `emailNotifications` when explicitly set, otherwise
  - account `preferences.emailStatusUpdates`,
- request is not completed or declined,
- request is not individually paused from follow-up automation.

Guest requests, owner-created requests without a linked verified customer profile, unverified accounts, and opted-out customers do not receive automated follow-up email.

These workflow reminders are transactional only. They must not contain promotions, discounts, gallery recommendations, or unrelated marketing content.

## Persistent follow-up data

Add a dedicated application collection for follow-up records and one singleton settings record.

### Follow-up record

```ts
type FollowUpType =
  | "quote"
  | "deposit"
  | "final-invoice"
  | "waiting-on-customer";

type FollowUpStatus =
  | "pending"
  | "sending"
  | "sent"
  | "deferred"
  | "failed"
  | "canceled";

type CustomerFollowUpRecord = {
  id: string;
  requestId: string;
  requestCode: string;
  customerAccountId: string;
  type: FollowUpType;
  stage: 1 | 2;
  anchorId: string;
  anchorRevision: number;
  dueAt: string;
  status: FollowUpStatus;
  subject: string;
  text: string;
  idempotencyKey: string;
  attemptCount: number;
  lastAttemptAt: string;
  nextAttemptAt: string;
  sentAt: string;
  resendEmailId: string;
  reason: string;
  createdAt: string;
  updatedAt: string;
};
```

The record ID is deterministic from the business event, for example:

```text
<request-id>:quote:<quote-id>:r<revision>:stage1
<request-id>:invoice:<invoice-id>:stage2
<request-id>:waiting:<waitingSince>:stage1
```

The subject and body are materialized before the first send attempt and remain immutable for retries using the same idempotency key.

### Follow-up settings

```ts
type CustomerFollowUpSettings = {
  enabled: boolean;
  updatedAt: string;
  updatedBy: "owner" | "system";
};
```

Default: disabled.

### Request follow-up control

Use a separate collection keyed by request ID rather than adding another workflow status:

```ts
type RequestFollowUpControl = {
  id: string;
  requestId: string;
  paused: boolean;
  waitingOnCustomer: boolean;
  waitingSince: string;
  waitingNote: string;
  updatedAt: string;
};
```

Default behavior for a request with no record is not paused and not waiting on customer.

## Candidate evaluation

Create a pure reminder-policy module. It receives requests, quotes, invoices, customer accounts, controls, follow-up history, and a supplied `now`.

It returns deterministic candidates with:

- reminder type,
- stage,
- anchor,
- due time,
- eligibility,
- block/defer reason,
- immutable subject/body inputs.

The pure policy must not read environment variables, hit Resend, write SQLite, or use real time internally.

This allows direct tests for all due/cancel/skip/cooldown cases.

## Cross-type cooldown and priority

A request may receive at most **one automated follow-up email in any rolling 24-hour window**.

If more than one candidate is due, priority is:

1. final-balance invoice,
2. deposit,
3. quote response,
4. waiting-on-customer.

Lower-priority candidates are deferred, not consumed. They may send after the 24-hour cooldown if they are still eligible.

The scheduler must never send multiple automated follow-up emails for the same request in the same sweep.

## Idempotency and duplicate prevention

Use defense in depth:

1. deterministic follow-up record ID,
2. persistent sent/failed state,
3. same deterministic Resend `Idempotency-Key` on every retry of the same logical email,
4. identical payload for all retries using one idempotency key,
5. one in-process scheduler instance guard.

Resend currently supports idempotency keys on email sends, with keys up to 256 characters and a 24-hour idempotency window. Application persistence remains authoritative beyond that provider window.

The existing in-app notification layer should support an optional deterministic notification ID for automated follow-ups so a retry cannot create duplicate profile notifications.

## Sending and retry behavior

Refactor the email portion of `customer-notifications.ts` only as much as needed to support a structured result and optional idempotency key.

The normal status-notification behavior must remain compatible.

For automated follow-ups:

- use a 10-second request timeout,
- retry transient network / 429 / 5xx failures with short exponential backoff inside the send attempt,
- do not retry 4xx validation/auth errors automatically,
- if a transient attempt still fails, persist `failed` plus `nextAttemptAt`,
- retry on a later hourly sweep with the same immutable payload and idempotency key,
- cap scheduler-level attempts at 3,
- expose exhausted failures to the owner.

No reminder should disappear because the process restarts.

## Reminder content

Reminder subjects are specific and include the request code.

Examples:

- `REQ-ABC123 — your Mesh Harbor 3D quote is ready`
- `REQ-ABC123 — deposit needed to start your print`
- `REQ-ABC123 — final balance reminder`
- `REQ-ABC123 — we’re waiting on your reply`

Body rules:

- identify Mesh Harbor 3D and request code,
- state exactly what action is outstanding,
- include the relevant amount for deposit/final balance when available,
- direct the customer to their Mesh Harbor profile for quote/payment actions,
- use HTTPS production links derived from `NEXT_PUBLIC_SITE_URL`,
- keep language factual and non-promotional,
- never include secrets or internal notes,
- do not mention owner-only workflow details.

v0.89 does not require a new marketing template system or React Email dependency.

## Scheduler lifecycle

Add root `instrumentation.ts`:

```ts
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { startCustomerFollowUpScheduler } = await import("./lib/customer-follow-up-scheduler");
    startCustomerFollowUpScheduler();
  }
}
```

The scheduler module:

- uses a global symbol / module guard so one Node process starts only one timer,
- schedules the first sweep after approximately 60 seconds,
- repeats hourly,
- uses `.unref()` when available,
- catches and logs sweep failures without crashing the app,
- does no work when the deployment gate is false,
- still permits owner-invoked preview regardless of deployment gate.

## Owner APIs

Add owner-authenticated, same-origin routes:

### `GET /api/owner/follow-ups`

Returns:

- deployment gate state,
- owner master setting,
- counts: due, deferred, sent last 7 days, failed,
- preview candidates,
- recent follow-up history.

No customer secrets or email-service credentials are returned.

### `POST /api/owner/follow-ups/preview`

Runs a read-only evaluation using the current production data and returns:

- candidates due now,
- candidates upcoming,
- blocked candidates and reasons,
- no email sends,
- no stage consumption.

### `PATCH /api/owner/follow-ups/settings`

Allows the owner to pause/resume the persisted master switch.

Requires owner session and same-origin validation.

### `PATCH /api/owner/requests/[id]/follow-up`

Allows the owner to:

- pause/unpause automation for one request,
- mark/clear Waiting on customer,
- set a short waiting note.

Marking Waiting on customer sets a fresh `waitingSince`.

Clearing it makes the current waiting candidate ineligible immediately.

## Versioning

Implementation changes package version:

```text
0.88.0 -> 0.89.0
```

No schema-version integer exists in the current generic SQLite record store, so no destructive schema migration is required. New collections are created naturally through the existing `app_records` table.

Backups automatically include these records because they snapshot the SQLite database.

## Testing strategy

### Pure policy tests

Cover:

- quote reminder at 47h vs 48h,
- second quote reminder at 5d,
- new quote revision invalidates old revision,
- approved/countered/declined quote cancels quote reminders,
- deposit reminders at 24h and 4d,
- deposit-paid cancels deposit reminders,
- partial deposit remains eligible,
- final invoice 24h reminder,
- overdue final invoice reminder,
- paid/void/uncollectible cancels invoice reminders,
- waiting reminder at 72h,
- clearing waiting flag cancels the candidate,
- re-marking creates a new waiting cycle,
- completed/declined request blocks all reminders,
- unlinked/unverified/opted-out account blocks email,
- per-request pause blocks reminders,
- 24h cross-type cooldown,
- priority ordering,
- max stages,
- deterministic IDs.

### Send/retry tests

Cover:

- idempotency key is stable,
- payload remains identical for retry,
- one in-app notification per reminder record,
- 429/5xx/network failures retry,
- 4xx fails permanently,
- max attempts stop,
- restart with sent record does not resend,
- failed record resumes when retry time arrives.

### API/security tests

Cover:

- owner authentication required,
- same-origin required on mutations,
- preview does not send,
- owner setting defaults off,
- request control mutation cannot edit unrelated fields,
- responses never include Resend API key or secrets.

### Existing regression suite

Retain and pass existing tests for:

- owner security / 2FA,

## Production rollout

1. Branch from current `main`.
2. Implement with TDD.
3. Set version to 0.89.0.
4. Run all local/CI validation.
5. Visually inspect owner UI.
6. Create and review PR.
7. Merge to `main`.
8. Wait for Railway terminal `SUCCESS`.
9. Check runtime and HTTP logs.
10. Verify `/api/health` returns 200.
11. Keep `CUSTOMER_FOLLOWUPS_ENABLED=false`.
12. Run production Preview / Dry Run.
13. Inspect every due candidate and blocked reason.
14. Confirm no stale/guest/unverified/opted-out recipient is eligible.
15. Enable the deployment gate only after the preview is clean.
16. Keep the owner master switch available to pause/resume automation.
17. Send one controlled reminder test to a verified test/customer account if available.
18. Confirm Resend delivery and follow-up history/audit state.

## Success criteria

v0.89 is complete when:

- reminder eligibility is deterministic and tested,
- duplicate automated emails are prevented,
- verified-email and preference gates are respected,
- quote/deposit/final-invoice/waiting reminders work at the defined cadence,
- owner can preview, pause/resume, and see reminder state,
- owner can mark a request Waiting on customer,
- failures are visible and retriable,
- production deploy is healthy,
- automatic sending is not activated until production preview is reviewed,
- existing payment, shipping, auth, upload, and backup behavior remains intact.

# Mesh Harbor 3D v0.88 — EasyPost Test-Mode Completion Design

Date: 2026-09-25

## Purpose

Finish v0.88 by activating and validating the EasyPost integration that already exists in the application, while preserving the new Owner Security work and preventing any accidental production-label purchase.

The existing EasyPost implementation remains the foundation. This release does not replace the shipping architecture or introduce a second shipping path.

## Current baseline

GitHub `main` is v0.88 and already contains:

- EasyPost rate creation for customer shipping quotes.
- Customer selection of USPS, UPS, and FedEx rates.
- Owner label purchase and refund actions.
- Shipment persistence and customer tracking display.
- EasyPost tracker webhook handling.
- Automatic-label-purchase support behind an environment flag.
- Owner Shipping / Security status UI.
- Operations Center EasyPost health summary.
- Owner audit logging around label actions.
- v0.88 owner 2FA, recovery codes, session revocation, security history, and backup verification.

Railway production currently has `EASYPOST_API_KEY` configured. At design time, the Railway variable list does not expose `EASYPOST_WEBHOOK_SECRET`, so signed webhook validation must remain a release blocker until that variable is present.

## Design principles

1. Reuse the existing EasyPost code and data model.
2. Test-mode EasyPost must be fully usable for integration validation.
3. Installing a live EasyPost key must not by itself enable live shipping.
4. No real postage may be purchased during v0.88 testing.
5. Owner UI must state exactly which EasyPost mode and protections are active.
6. Shipping failures must remain visible through the existing audit / Operations Center surfaces.
7. Existing authentication, same-origin checks, upload protections, Stripe flow, Resend flow, and persistent SQLite storage must not be weakened.

## Environment safety model

Add an explicit environment variable:

`EASYPOST_LIVE_ENABLED=false`

Rules:

- No API key: EasyPost is `unconfigured`.
- `EZTK...` test key: EasyPost is `test`; test workflows are allowed.
- Production EasyPost key + `EASYPOST_LIVE_ENABLED=false`: EasyPost is `production-locked`; the owner can see that a live key is present, but customer live-rate creation, label purchase, refund, and production EasyPost mutations are blocked.
- Production EasyPost key + `EASYPOST_LIVE_ENABLED=true`: EasyPost is `production`; production shipping actions are permitted.
- `EASYPOST_AUTO_BUY_LABELS` remains independently gated and defaults to false. It must remain false during v0.88 test validation.

The live-mode interlock is intentionally separate from key detection so accidental credential replacement cannot launch real shipping.

## EasyPost configuration status

Extend the existing EasyPost configuration summary with fields that distinguish:

- API key configured
- key mode
- live mode enabled / locked
- ship-from address configured
- webhook secret configured
- automatic label buying enabled
- connection test result and timestamp when available
- overall readiness state

Expected owner-facing states:

- Not configured
- Test setup incomplete
- Test ready
- Production key installed — live locked
- Production setup incomplete
- Production ready

The Operations Center and Security / Backups panel should use the same source of truth so the two views cannot disagree.

## Owner connection test

Add an owner-authenticated, same-origin-protected EasyPost diagnostic endpoint.

The diagnostic must:

- never return or log the API key or webhook secret
- make a harmless authenticated EasyPost request suitable for checking API credentials
- report success/failure and detected mode
- be rate limited or naturally owner-only enough to avoid abuse
- write an audit event for success/failure
- return a no-store response
- not create or buy a shipment as part of the simple connection check

Add a "Test EasyPost Connection" control to the owner integration-health UI.

## Full EasyPost test workflow

After the code deploys and Railway is healthy, perform these tests with the test key:

1. **Configuration**
   - `EASYPOST_API_KEY` is present.
   - `EASYPOST_WEBHOOK_SECRET` is present.
   - `EASYPOST_LIVE_ENABLED=false`.
   - `EASYPOST_AUTO_BUY_LABELS=false`.
   - ship-from address is configured in Owner -> Site Content.

2. **Credential test**
   - Run the owner diagnostic and confirm the test key authenticates.

3. **Rate test**
   - Use a controlled test request/quote with package dimensions and a test destination.
   - Request EasyPost rates through the application path.
   - Confirm only supported carriers/services are surfaced.
   - Confirm customer selection persists the EasyPost shipment/rate IDs and recalculates quote totals correctly.

4. **Test label purchase**
   - Use EasyPost test mode only.
   - Exercise the existing owner label-purchase path after required application payment-state preconditions are satisfied in the test workflow.
   - Confirm shipment/tracking/label metadata persist.
   - Confirm no production postage charge is possible because the credential is test-mode.

5. **Refund test**
   - Exercise the existing refund endpoint against the test shipment.
   - Confirm refund state persists and customer/owner records remain consistent.

6. **Tracker test**
   - Use EasyPost test tracker behavior to exercise at least pre-transit/in-transit/delivered and one failure/exception path where supported.
   - Confirm shipment status and tracking history update.

7. **Signed webhook test**
   - Confirm EasyPost can reach `/api/shipping/easypost/webhook`.
   - Confirm valid signed events are accepted.
   - Confirm an invalid signature is rejected.
   - Confirm replay/stale timestamp protection rejects old requests.
   - Confirm tracker updates are idempotent by EasyPost event ID.

8. **Owner/customer UI verification**
   - Owner Shipping controls show the test shipment.
   - Customer profile shows the test tracking state where appropriate.
   - Operations Center shows EasyPost Test Ready rather than production-ready.
   - No UI implies real shipping is enabled.

9. **Logs and health**
   - Check Railway build/runtime/HTTP logs.
   - Check `/api/health`.
   - Verify no new unhandled EasyPost errors.

Test records created solely for validation should be clearly marked and removed or left in a safely identifiable test state without deleting unrelated production data.

## Production transition

The live EasyPost API key will be handled only after the test workflow passes.

The later live transition requires:

1. Replace test key with live key.
2. Keep `EASYPOST_LIVE_ENABLED=false`.
3. Verify production-key authentication and webhook configuration without buying a label.
4. Review ship-from address and carrier setup.
5. Explicit user approval to enable live shipping.
6. Set `EASYPOST_LIVE_ENABLED=true`.
7. Keep auto-buy off for the first controlled real shipment unless separately approved.
8. Run one controlled real shipping workflow.
9. Verify carrier tracking and webhook delivery.
10. Only then consider automatic label buying.
